# 节拍坠落 / Beatfall

手机横屏四轨音游。导入自己的音乐，在浏览器内识别节拍与声音起点并自动编谱；在对应轨道任意高度点击、长按，或按箭头左滑、右滑、上滑。

[在线试玩](https://broken-star1999.github.io/musicgame/) · [GitHub 仓库](https://github.com/broken-star1999/musicgame)

参考用户提供的游戏视频，采用上窄下宽的透视轨道、向判定线靠近的音符、长按光带及击打粒子。保留四轨混合音符，舞台为原创程序绘制的霓虹背景。

## 本地启动

开发/构建使用 Node.js 22（CI）或 24（本次本机验证）。普通玩家只需打开网站，无需安装 Node.js、Python、模型服务或 GPU。

```bash
npm ci
npm run dev
```

打开终端显示的地址，通常为 http://127.0.0.1:5173/。首次进入会自动生成一首约 47 秒的原创演示曲和谱面，无需自行寻找音频。

```bash
npm test          # 核心节奏、谱面与判定测试
npm run build    # TypeScript 检查和生产构建
npm run preview  # 预览 dist 中的生产版本
```

## 两种识别方式

- **增强**：浏览器在本机运行 Beat This! small0，适合希望改善复杂伴奏下节拍跟踪的情况。模型约 9.4 MB、WASM 运行组件约 14.8 MB，首次未压缩资源合计约 24 MB；实际传输受压缩和缓存影响。无需 API Key 或独立模型服务。
- **轻量**：直接用频谱起音和节奏规则分析，不下载或运行模型，适合网络较慢或设备算力有限的情况。

在导入区切换即可重做当前歌曲分析，网站会记住选择。音频不会上传，模型和运行组件来自网站自己的静态文件。增强资源失败时会显示基础谱面提示，可以重新识别或改用轻量模式。两种路径都可能选错音乐层，建议先用自动演示观察；增强不是每首歌都更准。

增强加载会分别显示模型与运行组件的实际 KB/MB 进度。连接或下载连续 15 秒没有新数据时，自动使用已经完成的轻量结果；两项资源下载合计最多等待 90 秒。页面主线程还监控模型 Worker，45 秒没有进度便终止它并恢复轻量谱面，避免模型线程阻塞时一直等待。也可以随时点击“立即用轻量继续”，直接使用已有分析，不重复处理歌曲。

## 使用方法

1. 导入 MP3、WAV、M4A、OGG 或 FLAC 文件。最大 50 MB，时长 2 秒至 5 分钟；具体格式支持由浏览器决定。也可以直接使用内置演示曲。
2. 选择单指、二指、三指或四指，切换后在 Worker 中重新编谱，预览、游戏及结算显示同一档位。四档都使用四条轨道；除长按与滑动占用外，还会规划每根手指的落位、移动时间及交叉关系。生成时可取消，切换指法会终止旧任务。
3. 选择下落方式和速度。默认「透视推进」随轨道变宽平滑加速，使每秒位移与当前轨道宽度的比例保持一致；「屏幕匀速」保持恒定的屏幕纵向像素速度。两种方式都在同一时间到达判定线，速度设置只影响视觉提前量，不改变音乐节奏。
4. 网页默认使用横向布局，选歌、设置、游戏和结算保持同一方向。手机锁定竖屏时整页会自动侧转 90°，无需关闭系统旋转锁；自然横屏时正常铺满。四条轨道从顶部到底部均可触控，点击位置与画面上的透视轨道对应。
5. 下方为横跨四轨的双线判定框，音符到达框的下沿时踩点。可在对应轨道任意高度点击或长按；长按保持至尾部到达下沿；暖黄色滑动音符使用大号实心双箭头，从对应轨道起手，按方向短划至少 24 CSS 像素。轨道会越过判定框继续向下延展，未击中的音符穿过后淡出。
6. 歌曲结束后查看成绩，重试或返回选歌。自动演示可观察谱面，不记录最佳分数。

击中单点时，整个音符块会亮起并碎散消失；长按成功起手后，光带持续产生电弧和向上移动的脉冲，尾部完成时再闪亮一次；滑动额外带有方向光迹。特效围绕对应轨道与判定框绘制，不使用全屏闪白或震屏。

「音量、震动与校准」提供击打震动开关、音量、−300～+300 ms 判定偏移以及 BPM 修正。设备和浏览器支持 `navigator.vibrate` 时，手动成功击中会触发 10～16 ms 短震，长按首尾均有反馈，同时按键会合并震动；自动演示和 Miss 不震动。关闭开关或不支持此 API 时仍可正常游玩。正偏移代表判定时刻更晚，负偏移更早。BPM 修正仅影响接近节拍的起点对齐及节奏编排，不会把歌曲强行改成固定速度。

| 指法难度 | 谱面规则 |
| --- | --- |
| 单指 | 单指轮换，无同时按键；长按期间不插入其他操作。 |
| 二指 | 最多二指同时操作，可双押或长按搭配单点。 |
| 三指 | 最多三指同时操作，包含三押和更多长按配合。 |
| 四指 | 最多四指同时操作，重音可出现四轨同时按键。 |

每张谱面会显示所选档位、实际用指峰值、候选拍点和动作路线检查结果。安静、重音较少的歌曲不强行塞入多押，因此峰值可能低于档位上限。多押仍安排在实际检测到的声音起点，服从现有手指占用。首次访问默认二指，旧版简单/普通/困难分别迁移为二指/三指/四指，其余设置保留。

动作路线检查基于统一触控高度的参考手部模型：移动距离越远，需要的换指时间越多；长按中的手指保持占用，其他手指不能直接穿过。采用宽度 24 的束搜索，优先调整落轨，保留音乐时间；所有搜索分支都无法延续时才省略音符。该模型没有标定个人手长和具体手机宽度，实际舒适度仍需真机体验。

增强路径用本地模型估计拍点与候选重拍，再从真实声音起点选择主拍、半拍及更密细分。编谱先保留节奏骨架，再增加难度；长按需要新出现并持续的音高能量，滑动与多押按重音和乐句确定性编排。相似段落在节奏、音高及持续发音证据足够一致时复用按键模板，并保持各次实际起点。所有档位最后规划整段手指路线。轻量路径仍使用分频起音与连续节奏来源选择。完整实现和边界见 [ALGORITHM.md](ALGORITHM.md)。

Perfect 为 ±45 ms，Great 为 ±90 ms，Good 为 ±140 ms，超时为 Miss。权重分别为 1、0.75、0.4、0；长按首尾各为一个等权判定单位。分数归一化为 100 万，准确率为已判定单位的加权平均，Miss 中断连击。

手动暂停、切后台、系统取消触点或游玩中改变屏幕方向会暂停音乐和谱面。竖屏进入游戏时可直接游玩。恢复前倒计时 3 秒；如暂停时存在长按，需在倒计时内重新按住原轨道，未重新按住的长按尾部会判为 Miss。自动演示不需要重新按住。全屏是可选功能，浏览器不支持时仍可正常游玩。

右上角固定提供全屏按钮，选歌、游戏和结算时均可使用；进入全屏后点击同一位置退出。不支持全屏的浏览器会显示提示并继续保持横向页面布局。

## GitHub Pages

网站地址为 **https://broken-star1999.github.io/musicgame/**。

`.github/workflows/pages.yml` 会在推送到 `main` 时自动安装依赖、运行测试、构建，并发布 `dist` 到 GitHub Pages。仓库的 Settings → Pages → Source 使用 **GitHub Actions**。也可以在 Actions 中手动运行该工作流。

模型、WASM、字体和 Worker 都是网站自身的静态资源。Vite 使用相对资源路径 `base: './'`，使脚本、字体、图标和分析 Worker 同时适配 GitHub Pages 的 `/musicgame/` 子目录与 EdgeOne 的根目录。页面内部切换菜单与游戏，不需要服务端路由。

## 部署到 EdgeOne Makers

项目是纯静态应用，不需要 API Key、服务端或数据库。先把源码上传到自己的 GitHub 仓库，**不要上传 `node_modules`、`dist`、`.qa` 或个人音频/视频文件**。这些目录已加入 `.gitignore`。

在 EdgeOne Makers 中选择「导入 Git 仓库」，连接 GitHub 并选择项目：

| 设置 | 值 |
| --- | --- |
| 根目录 | 仓库根目录 |
| 安装命令 | `npm ci` |
| 构建命令 | `npm run build` |
| 输出目录 | `dist` |
| Node.js | 22 |
| 环境变量 | 无 |

这些构建参数也写入了根目录 `edgeone.json`。使用 HTTPS 部署，发布后检查首页、Worker 加载、音频导入和完整演奏流程。应用使用单页内部状态切换，没有需要单独配置回源的子路由。

可参考 [EdgeOne Git 部署说明](https://edgeone.ai/document/70404) 和 [edgeone.json 配置说明](https://pages.edgeone.ai/document/edgeone-json)。GitHub Pages 与 EdgeOne 可共用此仓库；EdgeOne 部署由仓库所有者在腾讯控制台连接后进行。

手机测试本地服务时，可以运行 `npm run dev -- --host 0.0.0.0`，在同一局域网用电脑的局域网地址访问。正式部署的 HTTPS 地址更适合验证手机兼容性。

## 实现结构

- `src/core/analysis.ts`：使用 fft.js 计算 1024 点实数 FFT，结合频率邻域最大值抑制、低/中/高频正向频谱变化、自适应阈值和局部峰值检测。用实际声音起点的间隔估计 BPM，并返回节拍支持度、能量包络和音频指纹。`analysis.worker.ts` 将计算放在 Web Worker 中。
- `src/core/beat-features.ts`、`beat-inference.ts`、`beat-decoder.ts`：模型特征、单线程 WASM 推理、块合并及保守拍点解码。
- `src/core/musical-events.ts` 与 `recognition.ts`：将模型拍点绑定到实际起音并赋予节奏层次。
- `src/core/onset-selection.ts`：先保留主拍骨架，再按层次和强度筛选落点。
- `src/core/rhythm-source.ts`：分段比较频段起音的周期支持度，以切换代价保持节奏来源连续；不把频段当成乐器身份。
- `src/core/chroma.ts` 与 `rhythm.ts`：4096 点独立音高特征、局部自相关、连续拍点动态规划、局部速度及弱支持度回退。
- `src/core/chart.ts`：从实际起点生成稳定的谱面；有限对齐节拍，基于持续能量编排长按，基于重音编排滑动；限制同轨间隔、长按重叠和同时操作数量。相同浏览器解码结果及难度产生相同谱面。
- `src/core/patterns.ts` 与 `phrases.ts`：原创乐句模式、持续音候选、拍坐标中的重复匹配与有界 DTW；限制比较数量，避免密集歌曲产生无界两两比较。
- `src/core/fingering.ts`：整段束搜索和显式手指分配回放，处理移动时间、长按阻挡、交叉及连续负担。
- `src/core/chart.worker.ts` 与 `chart-service.ts`：可取消的异步编谱，释放 Worker 并拒绝迟到结果。
- `src/core/chart-constraints.ts`：统一的用指占用、实际峰值及整张谱面可操作性检查；同时用于模板复用检查和页面统计。
- `src/core/judgment.ts`：独立、可测试的判定状态机，处理长按首尾、手势方向、暂停后长按重抓和分数。
- `src/core/haptics.ts`：可选的短震反馈、同时击打合并与暂停清理。
- `src/core/audio.ts`：音频解码、本地原创演示曲、单声道降采样和以 `AudioContext.currentTime` 为基准的播放时钟。
- `src/components/Game.tsx` 与 `renderer.ts`：Pointer Events 多触点追踪、暂停恢复和 Canvas 2D 透视舞台。音符位置由时间直接计算，丢帧不会累积位移误差。舞台光效参考已分析的能量包络。

内部谱面生成版本为 7：识别路径、音频指纹、指法难度、手指上限、时长、BPM、音符列表、乐句复用统计和指法规划报告。难度标识为 `one | two | three | four`。音符包含编号、0～3 轨道、秒单位时间及 `tap | hold | left | right | up` 类型；长按包含结束时间，最终音符额外记录 `finger` 分配。最佳成绩按生成版本、识别路径、指法和参考网格分别记录，不混用旧版成绩。无公共后端 API。完整算法及参考来源见 [ALGORITHM.md](ALGORITHM.md)。

音频、分析数据和谱面只在当前页面内存中保留。只有设置与最佳分数进入 `localStorage`；刷新后需重新导入歌曲。字体、图标和程序资源随构建打包，不依赖运行时字体 CDN。演示曲为程序原创合成，个人歌曲与参考视频未放入源码或构建产物。

自动谱面属于信号分析和游戏编排，不是精确的乐器转录或人工谱。复杂变拍、弱鼓点、混响较强的曲目可能有偏差；不同浏览器的解码/重采样细节也可能导致少量音符差异。

## 验证

`npm test` 覆盖已知 BPM 的合成鼓点、前置静音、变速片段、静音/极低音量拒绝、50 ms 起点误差目标、谱面可重复性、同轨冲突、难度上限、判定边界、四轨独立输入、滑动方向、长按松手、暂停后重抓及自动演示。

可使用本地歌曲执行额外分析测试，需要已安装 `ffmpeg`，歌曲路径通过临时环境变量提供，不复制歌曲到仓库：

```powershell
$env:BEATFALL_TEST_AUDIO = 'C:\path\to\your-song.flac'
npm test
```

该测试会输出 BPM、起点数量、四档音符分布和实际用指峰值，并检查同轨间隔、时长边界、长按与滑动占用、同时操作上限和重复生成。FFmpeg 与浏览器的重采样路径不同，数量可能略有差异。

版本 7 在桌面 Edge 中用《九万字 - 黄诗扶》FLAC 完成实际 WASM 分析，约 232 秒的歌曲本次分析约 21.9 秒；四档生成和操作约束检查通过。估计 BPM 为 130，不是人工确认的官方 BPM。154 项常规测试包含实际 WASM 与上游参考值对照、资源下载超时和页面侧 Worker 保护，私有歌曲测试默认跳过；设置环境变量后，该项也运行模型。没有对这首歌完成逐音符人工听感标注。

30 段、10 种风格的 GTZAN 开发比较中，±70 ms 节拍 F1 从版本 6 的 0.682 提升到 0.843；21 段改善、4 段持平、5 段退步。这不是全数据集的官方指标，也不是游戏准确率。逐曲结果与复现步骤见 [benchmarks/README.md](benchmarks/README.md)。

桌面 Edge 已检查完整导入、取消、恢复、触控、结算和重试；Android Chrome/Edge、iPhone Safari 的真实四指手感、蓝牙延迟、音频恢复与资源开销仍待真机验证。

详细验证结果见 `QA_REPORT.md`。轨道穿过双线判定框延展到画布底部；渲染与整轨触控共用透视几何计算，保证视觉边界与操作归属一致。

## 模型导出（仅开发者可选）

发布用模型已随源码提供，普通构建只需 `npm ci && npm run build`，不会运行 Python 或重新训练。若需重做导出，可在独立 Python 环境中先从官方 CPU 索引安装 Torch/Torchaudio 2.9.1，再安装 `scripts/beat-model-requirements.txt`，运行 `python scripts/export-beat-model.py`。脚本校验上游权重 SHA-256、原生推理及多种块长度的一致性，再写入带内容哈希的模型和配置；许可保留于 `public/models/BEAT_THIS_LICENSE.txt`。导出仅作转换，不训练权重。
