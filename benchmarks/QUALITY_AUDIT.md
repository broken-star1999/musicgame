# 真实音乐质量诊断与未采用的实验

日期：2026-10-30。生产编谱仍为版本 7，small0 模型及绑定/密度算法未改动。本轮增加的是自动演示可选的“落点音”，便于听出实际谱面头部的位置；提示音不是算法准确性的证明。

[逐曲指标与出处哈希](quality-audit-2026-10-30.json) 只包含数据统计，不含音乐、用户歌曲、音符时间列表或人工拍点原文。

## 已复现的不同问题

- `rock.00000` 的模型拍点在前两个十秒窗口 F1 均为 1.0，最后十秒降为 0.5；25 秒后相对人工拍点出现约 +86～163 ms 偏离。最终单指头三个窗口分别为 0.9189、0.8421、0.3846。这类误差在音乐事件绑定前就存在。
- `blues.00019` 有 62 个人工拍点，模型给出 125 个拍点、估计 247 BPM。绑定后 114 个事件中有 52 个参考匹配，单指筛选保留 59 个头但只剩 18 个匹配，并出现 4 次抽拍相位变化。所有落点仍是实测 attack，跟到另一节奏层不等于没有声音依据，但未必符合玩家期待。
- `metal.00019` 的异常短相邻模型间隔使主拍绑定窗口缩到约 20～28 ms，排除了部分真实声音候选。仅扩大窗口可能吸附其他节奏层，不能从一个失败样本推出通用修复。
- 模型 `confidence` 只反映当前峰值支持和保留关系；当原峰被全部保留时，公式会结构性偏高，不能解释为拍点正确概率。`rock.00000` 后段偏离而全曲支持度仍约 0.9902，就是例子。页面不把该值展示为正确率。

以上诊断使用现有开发样本及人工拍点，阶段最终指标复现已发布 WASM 报告。不代表《九万字》的主观问题已被认定为相同原因。

## 固定抽拍相位：拒绝

仅对单指连续至少 8 个模型拍的过密段，按局部拍长导出整数抽拍因子，并固定保留同一 beat ordinal 相位；模型 downbeat 有足够一致投票时优先，否则比较实测 attack 强度。没有移动或新增起音，没有按曲目调参。

| 开发 30 段逐曲平均 | 原版 | 原型 |
| --- | ---: | ---: |
| 单指头 F1，±70 ms | 0.777530 | 0.755600 |
| Precision | 0.839689 | 0.821240 |
| Recall | 0.742425 | 0.719473 |
| 过密段相位变化次数 | 33 | 0 |

2 段改善、2 段退步、26 段不变。`blues.00019` 的 F1 降为 0，`jazz.00000` 从 0.6992 降为 0.2586。相位连续并不保证选择了期待的主拍，因此该方案未进入生产。

## 主拍容差改用九间隔中位数：独立留出否决

先固定规则：只把主拍绑定容差的 span 来源改成附近最多 9 个正间隔的中位数；保留原 90 ms 上限、span×0.2、评分、候选优先级、half/quarter/free 及所有后续逻辑。没有根据单曲调参。开发 30 段单指头 F1 从 0.777530 微升到 0.781503，2 升、1 降、27 不变。

随后用未参与该规则选择的另一批 30 段，一次性运行发货 small0 的实际单线程 ONNX/WASM。选集预先固定为十类风格各编号 3、11、23，与开发集的文件名和精确解码 PCM 哈希均不重叠。原版/原型共享同一次推理，raw/decoded clock 完全不变，前后 240 张四档谱通过占用及完整手指路线检查。

| 新 30 段逐曲平均 | 原版 | 原型 |
| --- | ---: | ---: |
| 绑定主拍 F1，±70 ms | 0.761901 | 0.758680 |
| 绑定主拍 F1，±50 ms | 0.717016 | 0.713838 |
| 单指头 F1，±70 ms | 0.754223 | 0.751101 |
| 单指头 F1，±50 ms | 0.710852 | 0.707737 |

0 段改善、3 段退步、27 段不变。全部退步为 `blues.00023`、`jazz.00003`、`metal.00003`；其中 `jazz.00003` 单指 F1 从 0.415094 降到 0.333333，音符从 19 减到 14。该规则会扩大部分短窗口，也会收窄部分真实较长窗口，开发收益未迁移，因此保留原版算法，不再次针对这批留出调整参数。

公开等价来源为 [sanchit-gandhi/gtzan](https://huggingface.co/datasets/sanchit-gandhi/gtzan) 的 `4bd857132cb0e731bef3ec68558e7acc0a85f144`；逐项按 file 列匹配。锚点 `blues.00000.wav` 与原 marsyas 来源的整份 WAV 和解码 PCM 哈希相同，30 段输入共约 39.7 MB。标注来自 [Beat This! annotations](https://github.com/CPJKU/beat_this_annotations) 的 `fd9fcc0896cb78730bae735102c8753ef3a3badd`。

“留出”只说明未用于本次规则选择。GTZAN 包含相关歌曲，文件名/精确 PCM 分离不能证明艺术家或整首歌独立；也不据此新增上游训练数据独立性的断言。这些数据仍不是全 GTZAN 官方成绩或主观音游评价。

## 可复现与试听

在按数据来源条款取得对应 WAV、保留原文件名后，可用现有转换器和隔离实验脚本复核。它只在 `.qa` 写临时模块和报告，网站不会导入实验代码。

```bash
python scripts/prepare-beat-benchmark.py --audio LOCAL_HOLDOUT_WAVS --annotations .qa/beat-annotations/gtzan/annotations/beats --indices 3 11 23 --out .qa/gtzan-holdout-eval
node scripts/experiments/compare-beat-binding.mjs --data .qa/gtzan-holdout-eval --holdout --out .qa/reproduced-median-holdout.json
```

缺少缓存 logits 时运行发货模型；缓存需有模型、输入、推理源码与输出哈希。当前 30 段开发集的历史复现方式见 [README](README.md)。实验源块已变化时脚本会拒绝继续，避免把另一套算法当作原实验。

将脚本整理入仓库后，使用已验证哈希的留出缓存重跑，30 段输入/标注/logits 哈希、各档指标和全部聚合值与首次运行完全相同。报告 `publishedBaselineExact` 对开发集为 30；新留出不在原发布报告中，该字段为 0 表示没有对应旧行，不表示原型比较的基线发生漂移。

真实歌曲可在自动演示顶栏开启“落点音”，直接听见当前所选指法谱面的音符头。同一时刻多押只响一次，长按尾部不响；关闭、暂停、退出会清理提示音。它用于人工试听，不提供“准确率”结论。用户提供的《九万字》及本地试听片段仍只在忽略目录内，未公开分发。
