# 版本 8：纯算法编谱验证

本轮改进浏览器内的信号分析与编谱，不新增模型、不调整已有模型权重。默认路径为纯算法；模型辅助保留为主动选择项。算法细节见 [ALGORITHM.md](../ALGORITHM.md)。

## 先分开判断问题发生在哪一层

比较基线为 `27649b3811a084890b8968e2e7a4149df14eb3cb`。冻结的版本 7 纯算法在开发集 `0/7/19 × 10 genres` 上：实测候选对参考主拍的覆盖率为 0.8950，选源后为 0.6789，最终单指头 F1 为 0.5223。起音检测、来源选择和难度筛选都会损失参考拍，不能只调整播放偏移，也不能把“检测到声音”当作“选择了玩家期待的节奏”。

音频播放、绘制与判定仍共享 Web Audio 时钟。下述指标评价节奏选择，与游戏内 Perfect、准确率及 100 万分计分无关。

## 拒绝过的改动

最初候选直接加入第一帧峰，并将整曲全局选源改成逐窗口选择、加周期和相位记忆。它在受控半拍干扰场景表现很好，却在 `5/13/29` 的 30 段新音乐上损伤了前面的识别阶段：

| 逐曲平均，±70 ms | 版本 7 | 被拒绝候选 |
| --- | ---: | ---: |
| 单指头 F1 | 0.529208 | 0.533318 |
| 选源后参考拍覆盖率 | 0.688505 | 0.645783 |
| 推断拍点 F1 | 0.665052 | 0.598708 |

单指 F1 的微小收益掩盖了上游退步。进一步四格对照确认，直接加入第一帧和重写整段选源都独立造成损失；后者还会改变全局 BPM seed，让局部速度搜索排除原本的参考周期。该组合没有发布。`5/13/29` 从此只作已观察诊断集，不能再称为未见验证。

## 最终规则的范围

- 保留原整曲 Viterbi 选源，仅在实际来源交接时检查旧周期与相位是否仍受录音支持。初始主线不改；从开头就选错音乐层的问题仍可能存在。
- 第一帧没有前帧，不足以证明新的上升沿。边界候选在普通峰值去重前隔离，不参与选源、BPM、拍点或参考网格锚定；推断后只恢复首段选中来源的可能边界提示，避免吞掉邻近普通起音。
- 边界提示保持原时间。真实 PCM 回归发现，将它吸附到向前外推的参考网格会得到负时间并拒绝整首谱面，已修复。
- 在已选来源中为实测起音添加主拍、半拍、细分角色，优先保留较轻的主拍；不加入其他频段的事件、不凭网格造键。至少三个主拍绑定才启用，不以全局置信度作唯一开关。
- 未修改 BPM 的重新生成保留自动局部拍点，手动参考可以明确撤销。音符动作方向只在已选重音上编排，不声称识别了旋律的升降方向。

两个受控半拍场景中，最后部分的单指参考覆盖分别从 `0/63 → 63/63`、`0/319 → 319/319`；合法换源、120→150 BPM、连续加速和休止重启的原覆盖保持。生产选源与冻结原型在 36 组事件及六个完整 PCM 上精确一致。已观察的 60 段短音乐中，这项交接保护没有改变原选源；不能将合成结果写成真实歌曲后段均已修好。

首帧隔离加最终选源对 `5/13/29` 的 30 段检查中，普通检测事件、原 pulse、来源段、BPM 和整个拍点对象均与版本 7 精确一致；23 段只额外恢复一个选中来源的边界，7 段未加。拍点 F1 保持 0.665052；pulse 覆盖从 0.688505 到 0.689555。这是观察后的归因检查。

## 一次最终评价

最终选集在运行算法前固定为十类各 `00002 / 00017 / 00031`，共 30 段；未用于上面的调试。来源为固定提交的 [GTZAN 音频](https://huggingface.co/datasets/sanchit-gandhi/gtzan/tree/4bd857132cb0e731bef3ec68558e7acc0a85f144)及 [Beat This! annotations](https://github.com/CPJKU/beat_this_annotations/tree/fd9fcc0896cb78730bae735102c8753ef3a3badd/gtzan/annotations/beats)。和项目此前使用的 90 段相比，文件名及精确解码 PCM 均不重复；这不证明 artist、song 或上游训练数据独立。

参考范围统一为 `0 ≤ time ≤ PCM frames / 22050`，保留原始输入不改。旧 90 段共 4966 个参考均在范围内；最终集的 `reggae.00002` 有一个原标注位于音频结束后约 104 ms，按事先固定的共同边界排除，对基线和候选相同。

执行前冻结评价器、算法依赖、原数据和协议哈希；评价不去掉前导时间，不裁预测结果。预先固定的门槛为：单指 ±70 ms F1 绝对增益至少 0.02，±50 ms F1/精确率/召回率不降；按 genre 分层的配对 bootstrap（seed 20261030，10000 次）增益区间下界大于 0；pulse 覆盖率与拍点 F1 降幅各不超过 0.005；四档都合法且重复 JSON 一致。另要求每段四指谱的实测起手数量至少为版本 7 的 95%，先去重和弦，再检查实测候选 ±20 ms，避免以减少密集起音换主拍 F1。

四指具体旧起手的一对一保留率和来源路径变化另行完整报告；旧选择不是真值，数量保护也不能证明旋律跟随质量。30 段的小选集与 bootstrap 只描述这个固定比较，不能当作全部歌曲的正确率或主观好玩程度。

最终一次运行通过全部预先固定的门槛，原始参考 2193 个、有效 2192 个。30 段中 20 段改善、8 段退步、2 段不变：

| 逐曲平均 | 版本 7 | 版本 8 |
| --- | ---: | ---: |
| 单指头 F1，±70 ms | 0.521776 | 0.599024 |
| 单指头 F1，±50 ms | 0.476706 | 0.544227 |
| 单指精确率，±50 ms | 0.678264 | 0.699516 |
| 单指召回率，±50 ms | 0.384019 | 0.462624 |
| 选源后参考拍覆盖率，±70 ms | 0.678869 | 0.680387 |
| 推断拍点 F1，±70 ms | 0.679384 | 0.679384 |
| 四指平均去重实测起手数 | 82.4667 | 82.8667 |

单指 ±70 ms F1 的配对增益为 **0.077249**，条件性 95% bootstrap 区间 **[0.047147, 0.106844]**。每段四指实测起手数量比最低为 **98.86%**，与旧四指起手的一对一保留率逐曲平均 **99.08%**；基线和候选共 240 张谱均通过操作约束，每张完整重复生成一致。这 30 段的来源路径和推断拍点没有变化，提升主要来自编谱保留策略和首边界处理，不能归功于模型或声称节拍跟踪器本身全面提升。

## 复现

安装锁定依赖，并保留基线 commit 的 Git 历史。用 `scripts/prepare-beat-benchmark.py` 将合法取得的所选音频转换为 22050 Hz 单声道 f32le 和原始参考 JSON。仓库不提供这些音乐或完整标注数组。

```bash
node scripts/benchmark-signal.mjs --input <prepared-folder> --output .qa/signal-reproduction.json --protocol benchmarks/signal-v8-protocol.json
```

脚本从 Git 恢复基线的递归源码依赖，校验当前候选、评价器及整组输入哈希，再执行固定比较；输出逐曲汇总 JSON 和 paired CSV。协议与一次运行标记防止将看过结果后的调整当作同一场未见测试。原始音乐、私有歌曲、完整谱面及本机路径不进入公开报告。
